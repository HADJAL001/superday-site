Сохранять ссылку на существующий рабочий релиз до любых изменений.

## БЛОК 2. Исправить доставку GitHub → Forgejo — INFRASTRUCTURE

**Задача:** выбрать один согласованный путь, исключить параллельные неподконтрольные записи:

**Путь А — прямой GitHub Runner → Forgejo:** оператор из доверенной консоли подтверждает, что `64.177.120.183` принадлежит нужной машине; проверяет SSH listener, Docker-порты, host firewall и provider security rules, а также авторизованный источник входящих соединений. **Нельзя** отключать pinned `known_hosts`, делать SSH без проверки или открывать порт всему Интернету без сетевого решения. После исправления — manual workflow `Delivery to OSGARD (V15 verified Forgejo)` на актуальном `main`. Доказательство: артефакт с `outcome=success`, `reason=remote_sha_verified`, одинаковыми `head_sha` и `remote_sha`.

**Путь Б — внутренняя исходящая доставка:** если публичный SSH намеренно закрыт, доверенный оператор выполняет разработанный в [V16.1](OSGARD_FORGEJO_V16.md) `forgejo-local-recovery.sh` внутри одобренной инфраструктуры. Сначала `--check`, затем после проверки внутреннего SSH URL, ключа сервера и прав — `--apply`. Используются исходящий HTTPS к GitHub и разрешённый внутренний SSH к Forgejo. Нет `--force`, нет `--mirror`, нет изменения веток кроме `main`. Доказательство: `remote_sha_verified_after_push` или `remote_sha_verified_no_change`, повторная независимая сверка refs.

**Выход:** в Forgejo `refs/heads/main` содержит **текущий** GitHub SHA, записан run/artifact, транспорт и права подтверждены, выбранная схема передачи устойчиво обслуживается. В случае пути Б первоначальный workflow в GitHub может по-прежнему иметь красный статус — это не «починка прямого TCP»; его надо отдельно адаптировать лишь после согласования архитектуры.

**Блокер сейчас:** [инцидент #10](https://github.com/HADJAL001/superday-site/issues/10) открыт. Без владельца сервера ни одна правка README не может честно закрыть этот этап.

## БЛОК 4. Реальная функциональность и безопасность — PRODUCT ACCEPTANCE

Перед выпуском каждой нативной сборки протестировать по конкретному продукту его критические пользовательские пути из `OSGARD_RELEASE_TRACKER_V1.json` на тестовом окружении с разрешёнными учётными записями. Для функций, которых в продукте нет, явно указать `not_applicable`, а не изображать успешный ответ. Минимальный сквозной пакет:

1. **Сборка и версии:** воспроизводимый commit SHA, smoke на мобильных и ПК, JavaScript/серверные логи без критических ошибок, карта зависимостей и риск сторонних API.
2. **Данные и доступ:** RBAC/разделение аккаунтов, резервная копия перед миграциями, законное хранение и удаление данных, секреты в секрет-хранилище, не в репозитории/логах.
3. **Реальный core loop:** для SUPER DAY — создание/сохранение задач, API/voice по действительным возможностям; для NEW WORLD — проект/генерация/preview; для O2 — учёт/аудит; для OSGARDOS — основной рабочий сценарий; для MYOSA — запрос/ответ AI; для SENJORIO — настоящая заявка поездки; для VANGUARD — медиа-задача и полученный результат. Ни один успешный только HTML GET не закрывает этот пункт.
4. **Отказы:** API 401/403/429/500, тайм-ауты, связь после перезагрузки, повторный запрос/идемпотентность, уведомление пользователю без фиктивного успеха.
5. **Откат:** точный предыдущий образ/коммит, подтверждённая обратная процедура, запрет опасных откатов БД без плана совместимости.

**Выход:** протокол по каждому продукту с именованным исполнителем, датой, SHA кода/образа, реальными тестами, ссылками на артефакты, рисками и признаком `approved` или `blocked`. Отсутствующий протокол = `unverified`, не PASS.

## БЛОК 5. Единый релизный шлюз — EVIDENCE & GO/NO-GO

Существующая ежедневная V13-аттестация проверяет только байты публичной статики. Новый `scripts/osgard-release-readiness.mjs` связывает её с реестром исходников, независимой GitHub-проверкой утверждённых байтов V17 (`scripts/osgard-source-attestation.mjs`) и, при наличии, подтверждённым JSON доставки Forgejo. Заявление `github_main` в реестре без свежей аттестации исходного файла больше не считается доказанным исходником. Он выдаёт отдельный `OSGARD_RELEASE_READINESS.json` и отчёт GitHub Step Summary. Скрипт **не работает с production-секретами** и **не деплоит**.

**Условия перехода к ручной production-приёмке:** `7/7` утверждённых preview-байтов, `7/7` разрешённых нативных `main` источников, актуальный подтверждённый Forgejo SHA при использовании этого транспорта. Даже это только **`AWAITING_RUNTIME_SECURITY_AND_ROLLBACK_SIGNOFF`** — не полная готовность приложения.

**Окончательное разрешение:** отдельные подтверждённые протоколы из блока 4 и explicit go/no-go оператора/владельца продукта. В `OSGARD_RELEASE_READINESS.json` поле `full_production_release_approved` намеренно **false**, поскольку тест публичной статики никогда не должен сам подписывать функциональный/юридический релиз. Это архитектурное ограничение, а не ошибка.

**Выход:** решения основаны на ссылках на runs, SHA, отчётах и выполненных сценариях, а не на том, что «страница открывается».

## БЛОК 6. Публикация и откат — RELEASE

Выпускать продукты независимыми порциями, начиная с одного доказуемо управляемого нативного проекта, не одновременно всех семи. Сначала staging с точным SHA и тестами, затем canary/ограниченный live при поддержке текущего хостинга. Проверить 200/Content-Type/SHA на внешнем runner, загрузку всех WebP, отсутствие перенаправления на HTML/404, адаптивность 320/390/768/1280, нативные APIs, точность домена/TLS и метрики ошибок.

Перед live подготовить snapshot/backup и возврат последнего работающего релиза. Включить мониторинг 5xx, latency и failure-rate критического пользовательского действия. При регрессии — откатить конкретный продукт, не стирая данные и не блокируя шесть остальных. После этого повторить независимую проверку и зафиксировать операторский signoff.

**Выход:** семь отдельных доказанных production релизов, нулевой ложный PASS, документированный rollback и открытые инциденты только для действительно нерешённых задач.

## БЛОК 7. Эксплуатация и мировой уровень — OPERATE

В первые циклы после выпуска измерять *фактические*, а не выдуманные: завершение главного действия, ошибки, время отклика, crash-free sessions, повторное использование, стоимость облака/AI-инференса и скорость ответа поддержки. Сохранять телеметрию с согласиями, минимизацией данных и ограниченным сроком хранения. После стабилизации улучшать доступность, локализацию, производительность мобильных интерфейсов, WCAG, SEO, документы, платёжные интеграции и монетизацию по каждому продукту.

Глобальная оценка — это независимые пользовательские результаты и устойчивый SLA, **не 8K-анимация и не успешная сборка**.
